Project Aegis – App Constitution

Version: 1.0

Purpose: This document defines the permanent rules that every AI assistant, developer, and future contributor must follow. These rules must never be broken unless this document is explicitly updated.

1. Core Mission

Project Aegis exists to help one athlete recover, train, and perform better through intelligent, personalised coaching.

Every feature must support this mission.

If a feature does not improve recovery, movement quality, strength, or cricket performance, it should not be included.

2. Product Identity

The app is:

A Digital Physiotherapist
A Strength & Conditioning Coach
A Cricket Performance Coach
A Recovery Planner

The app is NOT:

A social network
A workout marketplace
A calorie tracker
A bodybuilding app
A step counter
A generic fitness app

3. Golden Principles
   Rule 1 – Recovery Comes First

No workout should increase injury risk.

Recovery always has higher priority than performance.

Rule 2 – The App Thinks

The user should never have to decide:

Which workout to do
Which exercises to select
How many sets to perform
How much to progress

The app decides automatically.

Rule 3 – One-Tap Experience

Daily flow:

Open App
↓

Recovery Check
↓

Start Workout
↓

Finish Workout
↓

Close App

The user should complete most sessions with one tap.

Rule 4 – Offline First

Everything must work without internet.

No feature should depend on a cloud connection.

Rule 5 – Simplicity

Every screen should answer one question only.

Example:

Dashboard → "What should I do today?"

Progress → "How am I improving?"

History → "What have I completed?"

Avoid clutter.

4. User Experience Rules

The application should feel:

Calm
Professional
Supportive
Intelligent
Encouraging

Never overwhelming.

Never noisy.

Never full of pop-ups.

5. Recovery Rules

The app must always check:

Pain
Stiffness
Sleep
Energy
Cricket workload

before recommending any workout.

No workout should be generated without this assessment.

6. Safety Rules

The app must:

Reduce workload if pain increases.
Replace unsafe exercises.
Recommend recovery instead of intensity when needed.
Never encourage training through significant pain.

Safety is always the highest priority.

7. Progression Rules

Progress must be gradual.

Progress only if:

Exercises are completed with good form.
Pain remains low.
Recovery score is acceptable.
Recent workload is manageable.

Never increase intensity aggressively.

8. Workout Rules

Every workout must include:

Warm-up
Main session
Cool-down

No exceptions.

Estimated duration:

15–45 minutes.

9. Exercise Rules

Every exercise must have:

Name
Category
Purpose
Target muscles
Difficulty
Equipment
Video
Coaching cues
Progressions
Regressions
Contraindications

No incomplete exercise records.

10. UI Principles

Every screen must:

Have one primary action.
Minimise scrolling.
Be usable with one hand.
Support dark mode.
Use large readable text.
Provide clear feedback.

11. Technical Rules

Mandatory technologies:

React Native
Expo
TypeScript
Zustand
SQLite
Expo Router
React Native Reanimated

No unnecessary libraries.

Keep dependencies minimal.

12. Coding Standards

Every feature must:

Be modular.
Be reusable.
Be strongly typed.
Include error handling.
Avoid duplicate code.
Follow consistent naming conventions.

Business logic must remain inside dedicated engines, not UI components.

13. Data Rules

All personal data stays on the device.

No cloud storage.

No analytics.

No advertising.

No tracking.

14. Coach Personality

The app speaks like an experienced coach.

Example:

❌ "Task Completed"

✅ "Great work. Today's mobility session is complete."

❌ "Error"

✅ "Something went wrong. Your progress is safe—please try again."

The tone should always be supportive and constructive.

15. Performance Rules

The app should:

Launch in under 2 seconds.
Navigate smoothly.
Save workouts instantly.
Avoid frame drops.
Use battery efficiently.

16. Feature Approval Checklist

Before adding any new feature, ask:

Does it improve recovery?
Does it improve coaching?
Does it reduce user effort?
Does it align with the app's mission?
Can it work offline?

If the answer is No to most of these, the feature should not be added.

17. Definition of Done

A feature is complete only when:

Functional
Tested
Matches the design
Works offline
Saves data correctly
Handles errors gracefully
Fits the coaching philosophy
Does not reduce app performance

18. Long-Term Vision

Project Aegis should eventually become:

A complete rehabilitation system
A cricket performance platform
A personal training companion
An intelligent recovery coach

While remaining simple, fast, and trustworthy.
